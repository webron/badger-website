# CLAUDE.md - badger.fit website

Astro site, deployed to GitHub Pages. The app it documents lives at
`/Users/ron/Development/badger-fit`. Site-only changes (layout, styling, typos, build) do not
need that repo's `CLAUDE.md` (25 KB); skip it. Open it only for questions about app behavior or the
release, and read just the section you need (`## Current release`, `## Feature Flags`, or the
`.claude/rules/` file for the area).

## Two rules that bind every session here

**1. Pushing `main` publishes.** `.github/workflows/deploy.yml` fires on push to `main`.
There is no staging step and no manual gate. So `main` may only ever describe what is live in
the stores.

Help for a feature that has not shipped goes on a `site/<topic>` branch, and those merge into
`release/<version>` as each one finishes. Only the release branch merges to `main`, on Ron's
word, when the app release goes live. A release's pages collide in the same three index files
(`src/components/HelpSidebar.astro`, `src/pages/guides/overview.astro`,
`src/pages/help/index.astro`), so merging as they land resolves one small conflict at a time
against a base that stays buildable.

After the last merge, build and check that every `#anchor` in those three files resolves to a
real `id=` on its target page. Git auto-merges sidebar entries happily and will produce a nav
that is internally consistent and links to nothing.

**2. All prose follows `../badger-fit/docs/writing_style.md`.** Structure, voice, and the
density budgets for constructions that read as machine-written. Before publishing:

```bash
../badger-fit/tools/prose_check.py src/pages/
```

The standard is shared with the app repo on purpose: the same person reads the store listing,
then the app, then a help page, and a change of register between them is noticeable.

**Marketing copy** (home page, guides, comparison pages, directory text, anything that pitches
Badger) follows the decisions in `../badger-fit/docs/marketing/` (about 29 KB, so only for copy that
pitches Badger; not for help pages, typos or build work). For that copy, read `decisions.md` and
`channels.md` there first, and record a new decision and the other channels you checked in the
same session.

## Keeping in sync with the app

Covered in badger-fit's `CLAUDE.md`, and all of it is a two-way obligation:

- A feature change updates its `/help/*` page and its line in `guides/overview.astro`.
- A new or renamed help page updates `HelpSidebar.astro`, `help/index.astro`, and the in-app
  list in `lib/features/about/presentation/screens/help_screen.dart`.
- Behavior affecting data collection or third parties updates `legal/privacy.astro` and
  `legal/terms.astro`, with the "Last updated" date bumped.
- The `.badger` files in `public/programs/` are generated by
  `badger-fit/test/tools/program_gallery_export_test.dart`. Regenerate them after a release
  version bump, since the page prints the app version read from the files.
- The spreadsheets in `public/programs/sheets/` are generated from those `.badger` files by
  `tool/sheets/` (`npm run sheets`). Regenerate them whenever the `.badger` files change, then run
  `npm run test:sheets`: it fails if a committed sheet is stale, and checks the formulas against
  LibreOffice when that is installed.

## Build

```bash
npm run dev      # local preview
npm run build    # CI runs it on every PR (.github/workflows/build.yml: build +
                 # test:anchors) and on push to main before deploying (build only).
                 # test:sheets is not in CI (fails on ubuntu-latest); run it by hand.
```
